# ETL 数据接入系统说明

## 1. 系统定位

本系统面向地理空间与产权类数据的规模化接入场景，提供一套**从异构源库到统一目标库的自动化数据接入（ETL）能力**。用户以配置化的方式登记数据来源、发起接入任务，系统即自动完成"抽取—转换—入库"的全流程处理，并实时跟踪任务的执行状态与进度，无需人工干预数据搬运本身。

整体采用**消息驱动、多阶段解耦**的处理方式：接入流程被拆分为可独立伸缩的几个业务阶段，阶段之间通过消息传递衔接，使单个阶段的吞吐波动不会直接冲击其它阶段，从而支撑大规模数据的稳定接入。

## 2. 业务背景与数据规模

系统服务于地楼房权人数据的大集中接入，典型数据体量：

- 约 15 万宗土地、65 万栋建筑、1300 万套房屋、约 1400 万条产权数据、2100 万实有人口；
- 语义地址库约 1200 万条。

数据既有普通属性字段，也含**空间几何信息**，因此目标存储需支持空间数据的保存与关联查询。

## 3. 接入方式

- 数据来源为**可直接连接的数据库**，系统按数据表进行抽取；
- **一个接入任务对应一张源表**的全量数据搬运；
- 目标端的接收表由系统依据源表结构**自动建立**，用户无需手工准备目标表。

## 4. 业务能力模块

- **数据源管理**：登记、维护待接入来源数据库的连接信息。
- **任务管理**：创建、启动、删除接入任务，维护任务状态与进度，是接入流程的编排与状态中枢。
- **数据抽取**：按任务从来源库读取数据，拆分为可处理的数据单元向下游流转。
- **数据转换**：对抽取到的数据做规范化加工，使其符合入库要求。
- **数据存储**：将转换后的数据写入目标库，并回报入库进度。
- **用户与权限**：提供身份认证与用户、角色、权限管理，保障接入操作的合规与可控。
- **统一接入网关**：作为对外请求的统一入口，负责请求转发、身份校验与访问流量控制。

## 5. 主要业务流程

1. **登记数据源**：用户录入并维护来源数据库的连接配置。
2. **创建接入任务**：用户基于某个数据源、指定要接入的源表与目标表创建任务，任务初始处于"待处理"状态。
3. **任务调度与目标表准备**：系统按既定周期发现待处理任务并抢占，读取来源表结构自动创建目标表，随后向下游派发抽取指令，任务进入"运行中"。
4. **数据抽取**：抽取阶段确定待接入数据的范围与总量，初始化任务的进度基线，并按批次持续读取源数据，将每条数据作为消息向下游传递。
5. **数据转换**：转换阶段对到达的数据并行进行规范化处理，加工后的数据向入库阶段流转。
6. **数据存储**：入库阶段将数据写入目标表，对重复数据做幂等处理，并按写入结果累计任务进度。
7. **完成判定**：当累计入库量达到任务总量时，系统认定任务完成，回写任务为"完成"状态并记录结束时间与处理量。
8. **失败处理**：任一阶段在重试仍无法恢复时，向任务管理回报失败，任务在未被判终态的前提下回写为"失败"状态并记录原因。

**任务状态**在业务上表现为：待处理 → 处理中 → 运行中 → 完成 / 失败。其中"处理中"用于避免多实例对同一任务的重复抢占。

## 6. 进度与状态协调机制

- 以任务为单位维护**总量与已完成量**的进度基线；抽取阶段确定总量、入库阶段按实际写入累加已完成量。
- 通过**进度到达阈值触发完成通知**的方式，实现分布式处理下任务完成的一致判定，避免依赖单一节点的判断。

## 7. 容错与可靠性

- **重试**：抽取与入库对可恢复的异常进行有限次重试，减少偶发故障导致的中断。
- **幂等去重**：入库对同一记录具备重复处理能力，消息重投不会造成数据重复。
- **异常数据隔离**：无法解析的异常数据被识别并跳过，避免个别脏数据阻塞整批处理。
- **失败状态回滚**：确认失败的任务状态被回写，保证任务状态真实反映处理结果（仅回滚任务状态，不撤回已成功入库的数据）。
- **单表全量、任务间隔离**：各任务相互独立，单任务的处理情况不影响其它任务。

## 8. 运行可观测性

- 提供任务运行日志与关键处理环节的指标（如各阶段处理量、丢弃量、耗时等），支撑问题定位与容量评估。
- 具备请求链路追踪能力，便于跨阶段排查一次数据流转的完整路径。
- 对关键运行指标设有监控与告警，异常可及时通知到运维。

## 9. 技术选型概要

- 微服务架构，各业务能力独立部署、协同工作；
- 以**消息队列**解耦接入流程的各处理阶段；
- 以**缓存/内存数据服务**支撑分布式锁、进度计数与幂等去重；
- 以**支持空间数据的关系型数据库**作为目标存储；
- 统一网关承担对外入口的鉴权、限流与请求转发。

## 10. 后续演进规划

### 10.1 演进动因（当前痛点）

现有接入链路以"多阶段 + 消息"横向解耦，在面向未来更大规模与更多来源时暴露出四类结构性痛点：

- **链路偏长**：一条数据要跨越抽取、转换、存储多个独立阶段与多次消息传递，端到端开销大、单条处理放大明显。
- **中间失败难定位**：缺乏贯穿全程的追踪与统一的失败数据归置，问题排查依赖逐段翻查。
- **是否结束难判断**：完成判定依赖进度计数的瞬时快照，源表在接入期间被并发写入时易出现"永远达不到总量"。
- **失败恢复难**：没有断点记录，重试等于从头再抽，无法只重跑失败部分；缺少人工干预入口。
- **接入面偏窄**：当前只支持数据库直连，尚不具备对文档、消息型等其他来源及持续流式接入的支持。

### 10.2 目标方向

围绕"**让接入更快、更可控、可覆盖更多来源**"，演进遵循如下业务与架构取向：

- **收敛处理链路**：将紧密耦合的抽取—转换—存储合并为一个处理单元在内部串联完成，消息通道只用于任务派发与进度回报，缩短一跳到底的路径。
- **引入统一编排与显式任务状态**：以一个编排中枢统一管理任务全生命周期，用明确的业务状态与迁移规则取代分散、随意的状态改写，并对终态加以保护。
- **断点续传与失败隔离**：以分片为单位记录处理进度（断点），失败只重跑受影响的分片；无法处理的数据进入隔离区，不阻塞整体；提供重试、取消、人工介入等操作。
- **进度判定更可信**：以持久化的处理进度作为完成判定的可靠依据，摆脱对瞬时快照与单点计数的依赖。
- **多来源可插拔**：以统一的接入接口抽象不同来源，逐步支持更多数据库、文档类（如 JSON/CSV/地理数据文件）等来源，避免"每接一种来源就新增一套处理"。
- **批量与流式并存**：在现有全量批处理之外，支持持续到达的数据以流式方式接入。
- **配套可观测**：贯穿全程的链路追踪、面向接入过程的指标与告警，使每个任务的健康状况一目了然。

> 取舍说明：面向当前数据规模（单表千万级、并发任务数十）与团队体量，优先以轻量自研的编排与断点机制达成上述目标，不引入重型编排框架；若未来并发显著上升或需要跨任务的依赖调度，再行评估。

### 10.3 分阶段路线

演进按可独立回滚的阶段推进，每一阶段都保持既有链路可用：

1. **观测与快赢优化**：先补齐追踪、指标与关键处理环节的批量优化，在不改变业务行为的前提下提升可观测性与吞吐。（**已完成**）
2. **处理单元与状态机**：建立统一编排中枢与显式任务状态、断点记录，新旧链路并行灰度、可比对回退。
3. **多来源接入与失败处置完备**：扩展文档类来源，补齐目标表主键、失败数据隔离与重试/取消等操作入口。
4. **流式接入**：上线流式处理通道，支持持续到达数据的接入与进度监控。
5. **旧链路下线**：新链路稳定承载后，逐步停用被合并取代的独立处理阶段，完成架构收敛。
